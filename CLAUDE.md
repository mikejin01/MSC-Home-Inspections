# MSC Home Inspections — working notes

One-page marketing site for MSC Home Inspections LLC. SvelteKit (Svelte 5),
static, and — since the WordPress conversion — deployable two ways from the same
source:

| Target | Command | Shape |
| --- | --- | --- |
| GitHub Pages | `pnpm build` | prerendered static HTML |
| WordPress on SiteGround | `make build-and-push` | client-rendered SPA inside a WP theme |

The live site is <https://mschomeinspections.com> (custom domain attached
August 2026; SiteGround's temporary `jeffl247.sg-host.com` hostname is dead —
it resolves nowhere, SSH included). Connection facts live in the gitignored
`.live-sites/msc.mk`, where `SITEGROUND_DOMAIN` drives both the SSH host and
the deploy path.

Full runbook: [`docs/WORDPRESS-DEPLOY.md`](docs/WORDPRESS-DEPLOY.md).
The architecture it implements: [`docs/SPA-TO-WORDPRESS-THEME-PLAYBOOK.md`](docs/SPA-TO-WORDPRESS-THEME-PLAYBOOK.md).

## 🛑 Never install WordPress locally

WordPress exists **only** on the live SiteGround server, reached over SSH. No
Docker, no `docker-compose` MySQL/PHP stack, no `wp-env`, no LocalWP, no
MAMP/XAMPP — not for development, not for testing, not "temporarily." The SPA
runs locally through `pnpm dev`; that is the whole local environment.

- The test environment **is** the live site: `make push` + WP-CLI over SSH.
  Need a throwaway? SiteGround Site Tools → WordPress → **Staging**.
- If the SSH connection facts are missing, **stop and ask the user** for them
  (see the table in the playbook §0.0). Missing credentials never justify
  improvising a substitute environment.
- `make test-connection` passing is the go/no-go gate. Nothing past Part 0 of
  the playbook happens until it does.

## Content sync rule (live WordPress is the source of truth for content)

Logged-in users edit text, images and links directly on the live site. Those
edits are stored in the WordPress database and **shadow** the defaults in
`src/lib/content.js`. The local copy is therefore possibly stale at any moment,
and nothing about the live site will look wrong while it is.

- **BEFORE editing** `src/lib/content.js`, `src/lib/content-overrides.json`, or
  any content key or default string in a component: run
  `make check-content-drift` (add `SITE=<key>` on multi-install setups).
- **If it reports drift: STOP.** Run `make pull-content`, review the diff, commit
  it (`chore(content): sync live edits from <site>`), and only then apply the
  requested change on top.
- **If SSH is unavailable**, say so explicitly and warn that local content may be
  stale. Do not edit content silently.
- **After deploying content changes** (`make build-and-push`), remind the user
  that database overrides still win over the new defaults. Clearing a stale
  override means deleting it (X.O. Admin → *Reset page content*, or
  `wp option delete xo_route_overrides`), not just redeploying.

Content resolution order, highest wins — the same list is in
`src/lib/wp/wpEdit.svelte.js`:

```
1. unsaved draft edits in the browser
2. xo_route_overrides           (per-route live edits)
3. post meta + xo_global_*      (WordPress database)
4. src/lib/content-overrides.json  ← what `make pull-content` writes
5. src/lib/content.js           (code defaults)
```

## Never hand-edit generated files

Everything under `wordpress-theme/` — `functions.php`, `index.php`,
`header.php`, `style.css` — is generated by
`scripts/build-wordpress-theme.mjs` and overwritten on every build. The
directory is gitignored and every generated file says so in a banner. **Edit the
generator, not its output.**

## Accessibility (WCAG 2.1 AA) — do not regress it

The site was audited and brought to AA in August 2026; the record, the numbers,
and the open items are in [`docs/ACCESSIBILITY.md`](docs/ACCESSIBILITY.md).
Three rules matter every time you touch styling:

- **`--accent` (`#1c6fc9`) is a fill colour, not an ink.** Accent-coloured
  *text* uses `--accent-ink` on light surfaces and `--accent-on-dark` on navy.
  `--accent-bright` is graphics-only — it is 3.75:1 against white.
- **Measure against the real backdrop.** The hero and contact tiles carry a
  radial glow over the navy gradient; check text against the glow's peak.
- **Visually hidden is not hidden.** A collapsed panel or an off-screen drawer
  needs `visibility: hidden` too, or its links stay focusable and its text stays
  readable to screen readers while `aria-expanded` claims otherwise.

Design tokens and the shared `bt-*` primitives now live in `src/app.css`, not in
`BentoPage.svelte`, so the legal pages share them. The header and footer are
`src/lib/components/SiteHeader.svelte` / `SiteFooter.svelte`.

## Adding a route is three edits

`/privacy-policy/`, `/terms-of-service/` and `/accessibility/` exist as real
routes. A new one needs all three of:

1. `src/routes/<slug>/+page.svelte`
2. the `THEME.pages` map in `scripts/build-wordpress-theme.mjs` — this is what
   creates the matching WordPress page; miss it and the route 404s on
   SiteGround while working fine on GitHub Pages
3. `LEGAL_LINKS` in `src/lib/content.js`, if it belongs in the footer's legal row

`xo_maybe_upgrade()` in the generated `functions.php` creates any missing pages
on the first admin request after a deploy, keyed on the theme version — the
theme is already active, so `after_switch_theme` never fires again.

⚖️ The privacy policy and terms are **generic templates** pending review by an
attorney, and carry `[Needs confirmation]` markers for the mailing address and
the analytics tools actually in use. Don't let copy edits quietly turn them into
claims the business has not made.

## Conventions worth keeping

- `src/lib/content.js` stays the single source of truth for copy. Components
  read it through `wpEdit.text(key, default)`; they never hardcode strings.
- Content keys are flat and stable (`hero_lead`, `service_pool_title`,
  `faq_2_a`). Keys prefixed `global_` are site-wide and become `xo_global_*`
  WordPress options; everything else is saved as a route override plus post meta
  under the `_xo_` prefix. Keys ending `_url` are sanitised as URLs; keys ending
  `_img` / `_photo` / `_logo` / `_mark` are treated as images.
- Renaming or reordering a key orphans the client's live edit for it. Prefer
  adding a key over renumbering one.
- Image paths in content are theme-relative (`/assets/images/x.jpg`) and get
  resolved by `assetUrl()` — never prefix them by hand.
- Prose in `content.js` is hedged on purpose ("signs of", "visible", "referrals
  for"). MSC inspects and identifies; it does not test, diagnose, or remediate.
  Do not let marketing copy drift past that line.
